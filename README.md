# Dictionary Next

Standalone Next.js version of the dictionary project, originally built for
HubSpot CMS.

This copy removes HubSpot CMS module fields and HubL templates. The app is
deployed on Vercel, while dictionary entries still load from the public HubDB
rows API. For now, the HubDB table remains the content source of truth.

## Commands

```bash
npm install
npm run dev
npm run build
npm start
```

## How The App Fits Together

This is a small Next.js App Router project. The server fetches dictionary data
from HubDB, then a client component handles the interactive alphabet filtering.

- `app/layout.tsx` is the root shell for every page. It loads global CSS, sets
  metadata, renders the shared header and footer, and runs a small boot script
  so the saved light/dark theme is applied before the page paints.
- `app/page.tsx` is the homepage route. It fetches entries with
  `getDictionaryEntriesFromHubDb()`, revalidates the page every 60 seconds, and
  passes the entries into `DictionaryBrowser`.
- `components/DictionaryBrowser.tsx` is the main dictionary UI. It is a client
  component because it uses React state for the selected alphabet filter.
- `components/DictionaryBrowser.module.css` contains styles scoped to the
  dictionary browser.
- `components/RichText.tsx` renders trusted rich-text HTML from HubDB. If the
  content source changes to user-submitted or otherwise untrusted data, sanitize
  the HTML before rendering.
- `components/SiteHeader.tsx` renders the local logo images from `public/`, the
  home link, and the theme toggle.
- `components/ThemeToggle.tsx` is custom client-side theme logic. Next.js does
  not provide a built-in front-end theme switcher here; this component changes
  `document.documentElement.dataset.theme` and stores the preference in
  `localStorage`.
- `components/SiteFooter.tsx` renders the footer.
- `app/globals.css` contains the global layout, typography, header/footer
  styles, and CSS variables for the light and dark themes.
- `lib/hubdb.ts` is the server-side HubDB client. It builds the HubDB API URL,
  reads environment overrides, follows pagination, and maps HubDB rows into the
  local dictionary entry shape.
- `lib/dictionary.ts` contains shared dictionary behavior: the `DictionaryEntry`
  type, alphabet list, sorting, grouping, HTML escaping, and excerpt/page
  formatting helpers.
- `data/dictionary.ts` is a checked-in static data snapshot target generated by
  `npm run import:hubdb`. It is not currently used by the live page.
- `scripts/import-hubdb.mjs` exports HubDB rows into `data/dictionary.ts`. This
  is the off-ramp to preserve the database in the repo before leaving HubSpot,
  but the live page would still need to be updated to import that local data.
- `public/dictionary-logo-light.png` and `public/dictionary-logo-dark.png` are
  the local logo assets. The app no longer depends on HubSpot-hosted logo files.
- `next.config.ts` is currently empty because no remote image host allowlist is
  needed for the local logo files.

## Data Source

By default, the app reads from:

```text
Portal: 21495103
HubDB table: 318438928
```

Override those values with:

```bash
HUBSPOT_PORTAL_ID=21495103
HUBSPOT_HUBDB_TABLE_ID=318438928
HUBDB_REVALIDATE_SECONDS=60
```

The page revalidates HubDB data every 60 seconds by default.

## Data Shape

The app expects entries with this shape:

```ts
{
  word: string;
  partOfSpeech?: string;
  definition?: string;
  excerpt?: string;
  page?: string;
}
```

`definition` and `excerpt` can contain trusted rich-text HTML from HubDB. If
this is later connected to a public form or untrusted external data source,
sanitize those fields before rendering.

## HubSpot Off-Ramp

To convert the public HubDB table to checked-in local TypeScript data later:

```bash
npm run import:hubdb
```

If the table becomes private again, run the same command with
`HUBSPOT_ACCESS_TOKEN`.

Run this before canceling HubSpot if HubDB content needs to be preserved in the
repo. The script writes `data/dictionary.ts`; after that, update `app/page.tsx`
to import the local data instead of fetching from HubDB.

Longer-term alternatives are:

- keep the dictionary as checked-in static data
- fetch from a private backend/API route using a server-side HubSpot token
- move the content into a database such as Supabase, Neon/Postgres, PlanetScale,
  Turso, or Airtable
